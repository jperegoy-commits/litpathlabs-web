LITPATH / FIELD MANUAL 01HOW TO READ THIS BOOK

The machine reports.

It does not confess.

You bought a machine with enough memory to make an ambitious idea look practical. Then a render slowed to a crawl while its queue said idle. A model answered ping through an outage. A successful request returned an empty string. Every instrument supplied a fact. None supplied the answer you needed.

This is a field manual about the distance between those two things.

The twelve plates come from a working lab: two ASUS Ascent GX10 systems built around NVIDIA GB10, with a Windows workstation alongside them. The incidents are small enough to recognise and expensive enough to remember. They are not a benchmark suite. They are the occasions on which a plausible interpretation survived until somebody opened the output, timed the job or read the next instrument.

The useful habit is simple: name what a reading proves, then name what it leaves untested. An empty queue proves that an engine has no queued work. It does not prove that the engine released its model. A finished HTTP request proves that a request finished. It does not prove that the result contains anything worth keeping.

The chapter device is THE LIE / THE TRUTH. Usually the instrument is not literally lying. The left column is the conclusion an operator is tempted to draw; the right is the observation that defeats it. Sometimes the bad conclusion came from our own runbook. Those are worth keeping in the book too.

Read a plate when the symptom appears. Read the three standing-order plates before it does. Keep a small known workload and a record of what it normally costs. They are more useful than a beautifully coloured dashboard with nothing calibrated behind it.

Who this is for

You operate a local AI workstation: model serving, image or video jobs, CUDA extensions, a few services sharing more memory than their separate dashboards admit. You can read a shell command and identify the service it addresses. You want fewer mystery outages and fewer confident explanations that fall apart at the next measurement.

This is an operator's incident book, not a setup guide or a replacement for the hardware vendor's recovery procedure. The GB10 examples are the centre of it; the same discipline often travels to other systems. The exact numbers do not.

How the evidence is marked

Observed: a value or outcome retained in the lab's dated incident records. The original records are curated operational notes, not a complete set of raw traces.

Reconstructed readout: a compact representation of those observations, with placeholder hostnames or omitted fields. Unless explicitly identified otherwise, terminal blocks in this book are reconstructed examples. A $ or PS> prefix identifies a shell, not text to paste.

Diagnostic recipe: a proposed check, with comments describing how to interpret it. No output is invented to make a recipe look tested.

Inference: an explanation consistent with the record but not isolated by a controlled experiment. An untested local prohibition stays a policy; it does not become a product defect.

LITPATH / FIELD MANUAL 01THE SHARED POOL

GB10 in ninety seconds

One physical memory pool is the organising fact. CPU work and GPU work can compete for that capacity. An idle model server, a compiler and a render engine therefore belong in the same admission decision. A process does not become cheap merely because it has no CUDA context.

Capacity is not bandwidth. A large pool may hold a model whose single-user generation remains slow. A small job may fit easily while saturating compute. Name the workload before deciding which resource limits it.

Unknown is not empty. On the observed GB10 Linux stack, aggregate framebuffer totals were unsupported while per-process GPU memory was available. Use the tools that report meaningful values on your own version. A blank field must remain unknown in your dashboard.

Occupancy is not pressure. Used RAM and occupied swap describe residency. Stall time, I/O and workload progress describe what that residency is costing. Both views matter.

File size is not peak runtime memory. Add context storage, temporary buffers, concurrency and the loader's behaviour. Keep a budget attached to a tested configuration.

Three measurements beat one verdict. What is resident? What is waiting? Is the requested work advancing? A useful health check answers the question you actually depend on.

PLATE 01 · PART I

THE N/A CARD

Failure class: blind instrument · Escape hatch: read free -g, attribute from the services

You open nvidia-smi because the box feels full and you want to know what is holding it. The header prints. Where the memory gauge should be — the one number you came for — there are two brackets and three letters: [N/A] / [N/A]. The tool that exists to tell you what is on the card has just told you it doesn't know. Meanwhile the render that made you look is crawling, and somewhere in the unified pool there is 75 GB of something you cannot name.

THE LIE / THE TRUTH

THE LIE — what the instrument reports

THE TRUTH — what is physically happening

Memory-Usage: [N/A] / [N/A]

The driver can't read the framebuffer, so there is nothing to worry about here. No number means no problem. Look somewhere else for your stall.

free -g → used 75 · available 45 · swap 15/15

available reads 45 in the recorded free -g output while swap is full and the job crawls. That combination calls for investigation; swap occupancy alone does not prove current thrashing. The card is not empty; the counter is empty. The memory you want to see is host memory, and job progress and memory-pressure measurements establish whether the host is struggling (Plate 05).

The gauge reads blank not because nothing is resident but because, on the GB10, the classic framebuffer totals are unsupported on the observed build. Grace-Blackwell shares one physical pool between CPU and GPU. nvidia-smi was written for a discrete card with its own VRAM, so memory.used and memory.total — the fields the whole ecosystem of monitoring scripts scrapes — come back [N/A]. The instrument is not broken. It is answering a question the architecture doesn't have: how full is the card's dedicated memory? There is no dedicated memory. There is one pool, and this tool cannot see it.

The incident, from the log

A render that normally finishes warm in about eight minutes was crawling at 265 seconds per step — a single six-step pass stretched to roughly 27 minutes, and still going. The first instinct is the right instrument, the wrong reading:

# 96% util looks like hard work. The two [N/A]s look like "nothing to see."
# Neither reading establishes useful progress; the missing total is unsupported, not zero.

The utilisation field says busy; the memory field says unknown. Reading unknown as empty is the mistake. So you stop asking the card and start asking the architecture:

$ free -g
              total        used        free      shared  buff/cache   available
Mem:            121          75           2           0          44          45
Swap:            15          15           0
# available reads 45, NOT free's 2 — and swap is full in this slow run.
# free reads 2 and looks fatal; available reads 45 (buff/cache 44 is the gap).
# Neither supplies a diagnosis by itself. Compare pressure and actual progress (Plate 05).

There it is — not on the GPU tool, on the memory tool. Now the second question: what is holding 75 GB. the aggregate gauge will not itemise it, but on this Linux box the per-process query does work:

$ nvidia-smi --query-compute-apps=pid,used_memory --format=csv
pid, used_gpu_memory [MiB]
<pid>, 7043 MiB        # a second render engine, idle — queue running:0 — squatting 7 GB
# The totals were [N/A]. The per-process figures are real.
# On Linux, ask per-process, not per-card.

The 7,043 MiB was a second render service sitting on the card doing nothing (Plate 07). Freeing it without stopping it — curl -X POST localhost:8190/free -d '{"unload_models":true,"free_memory":true}' — dropped its reported footprint to 355 MiB. Over the recovery interval, the host’s available rose 45 → 79 and swap occupancy fell 15/15 → 8/15. The stalled render finished. Those host deltas include changing system state; they are not all attributable to the one process (Plate 05). The per-process change was visible in nvidia-smi; the host-wide recovery needed a second instrument.

The lesson is procedural, not lucky. When the GPU tool goes blank, you do not stare at it harder. You change instruments: free -g for the pressure, --query-compute-apps for the culprits, and — where those still leave a gap — the services themselves. A render UI knows its own allocation (/sdapi/v1/memory → cuda.allocated.current); an inference server lists its resident models with sizes (/api/ps → size_vram per model); a second render engine reports its footprint (/system_stats; inspect its reported free and total values together). Those three endpoint/field names are the ones the render-UI and inference-server builds we run actually expose; a reader on different software needs the equivalent endpoint, not these literal paths. These accounting views can overlap and use different definitions. Do not add them into a supposedly exact ledger. Label unexplained memory unattributed until process and allocator measurements identify it; a desktop is a candidate, not an answer.

WHY THIS IS WORSE THAN IT LOOKS

A blank reading is more dangerous than a wrong one. A wrong number at least makes you argue with it. [N/A] makes you skip the memory question entirely and go hunting for a compute problem, a driver bug, a bad cable — anywhere but the one pool that is actually full. Every monitoring dashboard built on scraping memory.used inherits this blindness silently: the column is None on every row, not because the box is idle but because the field was never populated, and no amount of polishing that table will ever make it answer what is eating my card. The instrument that should raise the alarm is the one instrument guaranteed to stay quiet.

The Windows / Linux asymmetry — a callout worth memorising

The same tool lies in opposite directions on the two platforms, and knowing which way yours lies is the whole skill:

  • On the GB10 under Linux: the per-card totals (memory.used / memory.total) are [N/A], but nvidia-smi --query-compute-apps=pid,used_memory returns real per-process figures. Ask per-process, and back it with free -g.
  • On our Windows box (WDDM): the per-card total works, but --query-compute-apps returns [N/A] for used_gpu_memory on every process — the whole column is empty by construction. There is no free -g to fall back on either; you attribute entirely from the services (the render UI's memory endpoint, the inference server's model list) plus the "everything else" gap row. This WDDM per-process [N/A] behaviour is what we observe on our current driver/OS build; treat it as driver-version-specific — a GPU-driver update could quietly change it, so re-check before relying on it long-term.

NVIDIA documents unsupported aggregate framebuffer memory on this integrated-GPU platform, with per-process memory still listed. Our driver printed [N/A]; the exact display can change. A driver/library version mismatch is a different failure and must be diagnosed separately. See NVIDIA’s known issues.

Recovery & prevention

  1. When the gauge is blank, change instruments — don't re-run it. free -g first: read available, not free — but read swap in the same glance. On this die a comfortable-looking available does not explain a slow job. Here it read 45 while swap read 15/15 and the render crawled; investigate those observations together (Plate 05).
  2. Name every tenant before you blame the card. Compare the services that report their own footprint with host-wide measurements. Avoid double-counting shared allocations. Leave a gap unattributed until you measure its owner.
  3. free beats kill. A squatter usually has a /free endpoint that releases its memory without a restart — recover the GB before you kill the process and lose its warm state.
  4. Never wire an alarm to a field that reads [N/A]. Any dashboard column fed by memory.used is structurally blind on this box. Build the memory alarm on free -g available (Linux) or OS and service measurements (Windows), and delete the column that was always going to be None.

PLATE 02 · PART I

THE STUCK-BUSY MISMATCH

Failure class: misread wedge signature · Escape hatch: diagnose by step rate, never by the idle triad

A render is running and you glance at the card to check on it. nvidia-smi gives you three numbers that, on any discrete GPU you have ever owned, mean exactly one thing: utilisation pinned at 96%, the SM clock floored near idle, power draw down in the single watts. Our old runbook calls that triad stuck-busy. It is a suspicion, not a diagnosis. You are about to declare a wedge and reboot. The numbers are real. The verdict is wrong, and the reason it is wrong is that these fields did not distinguish the two states in our observations.

THE LIE / THE TRUTH

THE LIE — what the instrument reports

THE TRUTH — what is physically happening

utilization.gpu: 96 % clocks.current.sm: 721 MHz (max 3003) power.draw: ~6 W

Pinned at 96% but clocked at idle and sipping single-digit watts — the classic stuck-busy mismatch. High utilisation paired with abnormally low power is a card paging, not computing. This render is wedged.

That exact reading — 96% util, 721 MHz, ~6 W — is what a perfectly healthy render produced, ticking along at 56 s/step, nothing wrong with it at all. These observations do not establish what the clock and power fields were measuring, or why. They only show that our chosen thresholds were not diagnostic. And the clock barely moves between the two states: a healthy render read 721 MHz, a genuine post-OOM wedge sat at 728 MHz — a hair apart, both at 96% util. Power stays uselessly low in every figure we have. Measured job progress is the stronger evidence here.

Our discrete-GPU runbook had promoted a heuristic into a verdict. High utilisation, a low reported clock and low power can justify investigation, but they do not establish paging or a stuck kernel on any architecture. A clock may really be low; a sensor may report only one power domain. The unsupported memory-total field in Plate 01 does not prove that these different counters are unsupported too. Keep the observations. Discard the unsupported explanation.

A render is running and something about the card feels wrong, so you check the counters — and the triad screams wedge. You go to the card ready to reboot it:

Believe that triad and you reboot a working machine. So you stop asking the card how it feels and ask the job how far it has got — the step rate from the progress bar:

$ docker logs --tail 2000 <engine> | tr '\r' '\n' | grep '%|'
 42%|████▏     |  ...  56s/it
# tqdm writes each update with a CARRIAGE RETURN, not a newline. `docker logs --tail 5` shows
# an unhelpful view of progress. Split \r to \n and check timestamps and new steps.
# 56 s/it is well inside normal for this pass. Not wedged. Just quiet, on a card that can't
# tell you it's busy.

Fifty-six seconds per step is healthy. The clock said idle; the bar said working; the bar was right. That is the whole plate in two readings.

Now the other half — because the wedge is also real, it just doesn't announce itself in the triad. On the day it genuinely happened, an inference process and a render collided in the one unified pool and the kernel logged an honest out-of-memory:

$ dmesg -T | grep -i nvrm
... NVRM: nvCheckOkFailedNoLog: Check failed: Out of memory [NV_ERR_NO_MEMORY]
# ~6 seconds after the inference process logged "Device 0: NVIDIA GB10 ...". Two tenants,
# one pool, no MIG to wall them off. This is the actual failure (Plate 05).

The damage was measured off the render engine's own execution timestamps, not guessed: one clip took 102.9 minutes, the next 65.3 minutes, against the ~8-minute warm baseline — an 8–13× penalty, not the "twice as long" it felt like. And the clock? Afterward it sat stuck at 728 MHz at idle, long after the render finished — a hair off the 721 MHz the healthy render had shown. Similar clock readings, different measured performance.

WHY THE INSTRUMENT CANNOT TELL THEM APART

Our records show 721 MHz during a healthy render and 728 MHz after a severe slowdown. They also record about 6 W during healthy work and 21 W on a separately troubled worker. These are different observations, not a controlled sensor calibration. We cannot derive a universal threshold or declare the sensors meaningless. We can reject the threshold that would have condemned the healthy run. Compare the same workload’s elapsed time, step progress and output before deciding what to repair.

The trap has a second edge, and it bit on recovery. After applying the first-aid free (curl -X POST localhost:PORT/free -d '{"unload_models":true,"free_memory":true}'), the idle clock still read 728 MHz — so by the clock, the wedge had not cleared. It had. Proof came from behaviour, not the counter: a fresh known render completed in 7.2 minutes against its ~9-minute baseline, output verified real end to end. The low clock did not confirm the fix. Behaviour under a fresh load is the test; the idle reading is not.

Recovery & prevention

  1. Diagnose a wedge by step rate, never by the idle triad. Read the progress bar, splitting carriage returns first: docker logs --tail 2000 <engine> | tr '\r' '\n' | grep '%|'. A short --tail 5 can conceal progress; compare timestamps and the engine state.
  2. If no bar has flushed yet, prove liveness another way — the engine's queue endpoint showing the job running, plus a hand-timed wall-clock delta between two steps. Do not read "no new line" as "hung"; buffering and carriage-return rendering can hide updates; flushing behaviour depends on the process and its output stream.

  1. The real test that a wedge cleared is behaviour under a FRESH load, not the idle reading. The SM clock stayed at 728 MHz after the fix that worked. Run a small known job and time it; trust the stopwatch, not the counter.
  2. Know the actual cause so you fix that, not the symptom. In this incident, the evidence pointed to memory pressure — two tenants sharing one pool with no MIG (Plate 05), confirmed by NV_ERR_NO_MEMORY in dmesg. The cure is free first, then load (Plate 09), not a reboot on the strength of a clock reading.

There is no GB10 wall-power baseline in this record, and no experiment establishing the physical meaning of the reported power values. We therefore do not convert six watts into a claim about the whole machine. A future driver or firmware update may change both counters and performance. Record that software level with your baseline and repeat the small reference job after an update. A useful instrument is one you have calibrated against work. The name of the counter is not its calibration.

PLATE 03 · PART I

PING IS NOT HEALTH

Failure class: false liveness · Escape hatch: health-check the layer that fails — a real fork, a real device-touching endpoint

You loaded a model that didn't fit and the box went quiet. You ping it out of reflex, and it answers — instantly, 0% loss, sub-millisecond. So the box is up. You ssh in to fix it, and the connection dies before it prints a prompt. You ping again: still perfect. The two facts sit on your screen refusing to agree, and the wrong one is the one that feels most like proof.

THE LIE / THE TRUTH

THE LIE — what the instrument reports

THE TRUTH — what is physically happening

5 packets transmitted, 5 received, 0% packet loss rtt ... time=0.26 ms

The box is up. It is on the network, it is answering, latency is perfect. Whatever is wrong, it isn't the machine — go check the cable, the bridge, the service config.

kex_exchange_identification: Connection closed by remote host

The host’s network stack is responsive. ICMP does not test whether the required application can work. The required remote shell and services did not respond in this incident. It is reachable and completely unavailable at the same time. Ping tested a layer that never went down.

An echo reply exercises the network stack. It does not require a successful application request or a new login shell. Do not turn that narrow success into a statement about every process on the machine. Conversely, a failed SSH handshake does not by itself prove memory exhaustion. In this incident it arrived immediately after an overcommitting load, alongside failed service requests and heavy disk activity. That combination, rather than a single error string, supported the pressure diagnosis.

The incident, from the log

A large inference host had a resident model holding 109 GB of a 121 GB unified pool. free -g read 12 GB available. A second model — 17.4 GB — was loaded into that 12 GB to test a service slot. Both numbers had been on-screen two tool calls earlier (that ordering failure is its own plate — see Plate 09). The box went into swap thrash and did not come out.

The first instrument said everything was fine:

Our remote escape hatches were ssh, a bridge daemon, and a repair deck, all of which terminate in a shell on the far side. When userspace is dead there is no software path in. It ended in a hard power cycle.

WHY THIS IS WORSE THAN IT LOOKS

A host that stops answering everything at least makes the loss of service obvious. A box that answers ping at 0.26 ms while unable to fork a shell steals your time in a specific way — it sends you looking everywhere the machine isn't. You check the bridge, the switch, the service config, the firewall, DNS, the port. Ping keeps telling you "the box is fine," so you keep believing the fault is between you and it. The false liveness is not a harmless extra reading; it is an active pointer aimed away from the answer. In our incident the bad state persisted for thirty minutes. File-backed reclaim and refaulting were the recorded explanation, not a proved rule that all memory-mapped loads evade the OOM killer. The practical lesson is to set a recovery deadline and use independent evidence; neither a ping reply nor an absent OOM line is a promise of recovery.

Health-check the layer that fails

The rule the incident teaches: a health check is only worth anything if it touches the layer that breaks. Ping touches the kernel network stack — the layer least likely to fail on an overloaded box, which is exactly why it lies. A real check forces the machine to do the thing you need it to do.

  • To prove userspace can run: force a fork. ssh -o BatchMode=yes -o ConnectTimeout=5 <box> true returning 0 demonstrates a remote command completed. A failure has several possible causes; inspect the error and correlate it with other probes. A successful remote command tests more than a bare ping.
  • To prove a service is alive, hit an endpoint that reaches the device, not the router. A web server's / can be served by the HTTP front-end while the worker behind it is wedged — we have watched a render backend accept a submission and hand back a real job id in 82 ms while its GPU worker was dead. The probe that caught it was the endpoint that touches the torch/device layer (/system_stats), which returned HTTP 500 the whole time / returned 200. Health-check the deepest layer you depend on, not the shallowest one that answers. That /system_stats path is specific to the class of render backend we run; on your own software, find the endpoint that forces the device layer to answer — not / — rather than assuming this literal path exists.

Recovery & prevention

  1. When ping and ssh disagree, believe ssh. Ping proves the kernel schedules interrupts and nothing more. If ssh <box> true cannot return an exit code, the box is unavailable regardless of what ICMP says. A banner-exchange failure is not an OOM diagnosis by itself; authentication policy, connection limits and network failures also need consideration.

SILENT SUCCESS

Failure class: the empty result that files itself as done · Escape hatch: assert non-empty, budget for the hidden reasoning, fail honestly

You point a vision-analysis call at a folder of six images and walk away. It comes back green: every call returned success: true, no error in the log, the catalogue written and closed. THE LIE / THE TRUTH

THE LIE — what the instrument reports

THE TRUTH — what is physically happening

{"success": true, "analysis": ""}

The call completed. The status field says success — no exception, no timeout, nothing thrown. The description just happens to be an empty string, and an empty string is a valid value. Write it to the record and move on.

The model never emitted an answer at all. The output-token budget is shared with the model's own hidden reasoning, and the reasoning ate the entire budget before a single content token was written. The call really did run — that part isn't a lie — but "ran without error" and "produced a description" are two different facts, and only the first is true. The artifact is empty because the answer was never born, not because the answer was short.

On the reasoning-enabled builds in this incident, the output budget had to cover reasoning as well as the visible answer. Parameter names and accounting differ across APIs and model templates; inspect the returned usage and stopping fields. A clean transport response does not guarantee that a model supplied usable content. Our wrapper needed a separate artifact check, not another interpretation of HTTP success.

The incident, from the log

The report was precise: a cataloguing run "will properly identify the first or second picture, but then just fill in the rest as blank." That shape — the first one or two succeed, the rest go empty — is the tell. The shape prompted a budget test; it did not establish a cache-related cause.

WHY IT NEVER SELF-HEALS

A blank counts as done. That is the whole trap. The cataloguing tool wrote each empty string into its record as a completed entry, and a completed entry is never retried — so on the next run the blank entries are skipped as already-processed, and the gap becomes permanent. It is not a transient that clears when you re-run; re-running is precisely what preserves it. This is the same family as every silent-artifact failure in this book: the status field is green, the log is clean, and the thing you actually wanted was never produced. No error will ever lead you here. The only evidence is the artifact itself — which is why you find it weeks later, by opening the file, not by reading the log.

Recovery & prevention

  1. Never return empty as success. A call that produces no content is a failure, whatever the status field says. Wrap the call so an empty result raises, retries, or is filed as an explicit error — never as a done record. On our box the fix was a wrapper that retries once at 2.5× the budget and hard-fails if content is still empty, plus a catalogue writer that refuses to file a blank so the next run retries it.
  2. Budget for the reasoning, not just the answer. Where the runtime shares one generated-token budget, it must cover reasoning and the answer. Measure representative prompts and leave room for both reasoning and the requested answer. On our vision build, answers only became reliable at num_predict = 2000; the 300-token budget was unreliable for the observed reasoning lengths. That 2000 is this build's working floor, not a universal constant — measure your own model rather than inheriting ours.
  3. Assert on the content, never the status. Read the returned string and check it is non-empty, complete and fit for its intended use before recording the call as done. success: true and finish_reason: stop are both true and both useless as proof of an artifact.
  4. When a whole class of output is mysteriously empty, count the artifacts before theorising. Counting blank entries made the failure measurable. The evidence is on disk, not in the log.
  5. On a health probe, give a reasoning model room to think — and read the reasoning field. A probe with max_tokens below the model's thinking length reports a healthy model as dead. Give any reasoning-model probe enough budget to clear the deliberation (≥ ~200 tokens on the model here) and inspect the reasoning field, not just content, before concluding anything is wrong.

Scope. The "generated-token budget includes the hidden reasoning" behaviour is confirmed here on two runtimes — Ollama (num_predict) and our OpenAI-compatible server (max_tokens) — but only with reasoning-emitting models. A non-reasoning model can also return empty or incomplete content for other reasons. It does not have this particular reasoning-budget mechanism. Confirm which kind of model you are on before quoting this as universal.

PLATE 05 · PART II

HOST PRESSURE IS GPU PRESSURE

Failure class: two-budget thinking on a shared-memory machine · Escape hatch: measure headroom, pressure and progress together

The render is crawling at 265 seconds per step. You check GPU utilisation, then check host memory, as though the two instruments describe separate budgets. One says busy. The other says there is room. On this machine the allocations draw from the same physical memory, but neither number explains how much useful work is getting done. You need a third question: what is the machine spending its time waiting for?

THE LIE / THE TRUTH

THE LIE — the convenient reading

THE TRUTH — the measured limits

GPU: 96% · available: 45 · swap: 15/15

The GPU is busy and the host has headroom. Alternatively, swap is full, so the machine must be thrashing. Pick whichever number agrees with your first guess.

render: 265 s/step

The job is slow. Those occupancy counters are context, not a complete diagnosis. Host and GPU workloads share capacity; current reclaim, I/O and job progress tell you whether that shared capacity is under harmful pressure.

The architecture matters because a host allocation can reduce room for a GPU workload. It does not make every GPU failure a memory failure. A kernel bug, poor batching, a slow disk or an expensive computation can still be the bottleneck. Shared memory changes the budget; it does not abolish diagnosis.

Read an estimate as an estimate

MemAvailable estimates memory that can be supplied without swapping. It includes some reclaimable memory as well as completely unused memory. Clean file-cache pages can be discarded and read again from their backing files; they do not require an empty swap slot. Full swap therefore does not make all reclaim impossible or invalidate available automatically. Linux memory concepts distinguish file-backed and anonymous memory.

The opposite mistake is spending the entire estimate. A future model load needs weights, context storage, runtime buffers and transient allocations. Some memory is pinned or otherwise constrained, and device allocators have their own reporting limits. A host estimate is a planning input, not a guarantee that a particular CUDA allocation will succeed.

WHY OCCUPANCY IS NOT PRESSURE

A swap area can remain occupied after the original pressure has passed. A snapshot tells you that pages are there; it does not tell you whether the machine is currently shuttling them in and out. Likewise, high memory use may be a productive cache or an oversized working set. Diagnose from movement and delay: swap-in and swap-out rates, memory-stall time, I/O latency and the job's progress. Then compare the same signals after a controlled release.

  4. Measure recovery at both layers. More available memory demonstrates headroom. Faster steps and a valid output demonstrate a recovered job. One does not substitute for the other.
  5. Budget the whole workload. Leave room for context, temporary buffers, the OS and the other services that must remain live. An on-disk weight file is only part of that budget.

The pool is shared. The counters are partial. Read enough of them to explain the work.

THE IDLE SQUATTER

Failure class: silent VRAM squat · Escape hatch: the engine's own /free, before the render, not after

A render that finishes warm in about ten minutes is forty minutes in and still crawling. You go to the render engine and ask it what it's doing: nothing. Its queue is empty — no job running, none pending. Every instrument agrees the box is free. So why is the render dying? Because a second service that stopped working hours ago never gave its memory back, and on this die the memory it is squatting is the same memory your render needs.

THE LIE / THE TRUTH

THE LIE — what the instrument reports

THE TRUTH — what is physically happening

queue running:0 pending:0

The engine has nothing queued and nothing running. It is idle. The card is free. There is no reason a fresh render should be slow — go ahead and submit.

<pid>, 7043 MiB # that same "idle" engine

An empty queue is not an empty card. The service finished its last job and kept 7,043 MiB resident — model weights it will not touch again until you queue something. On a unified die that 7 GB is not idling harmlessly on a spare card; it is holding down the one pool your render is trying to allocate from, and it has driven the box into swap.

"Queue empty" and "card empty" are two different facts, and the gap between them is this whole plate. A render engine reports on its work — jobs running, jobs waiting. It does not report on its footprint, and most of them hold their loaded weights resident between jobs on purpose, so the next submission starts warm. That is a reasonable optimisation on a machine with a dedicated card doing one thing. On a GB10, where every service draws from the same pool as every other service and as the host itself (Plate 05), an idle engine holding several GB is not warm — it is a squatter, and it is charging rent in render time.

Generate all your stills first, unload the render UI, then start the video render; free every other resident engine before a heavy job on the shared die. An idle engine holding memory is the most polite failure in this book. It breaks nothing, logs nothing, and answers every question you ask it honestly — "am I running a job?" "No." The question it never volunteers, and the only one that matters, is "am I still holding the card?" On a machine where the card and the memory and the host are one pool, that is the question you have to learn to ask before every render.

Failure class: a build treated as "not a GPU job" · Escape hatch: cap MAX_JOBS, free residents first, and kill the tree correctly

You needed to build a CUDA extension. There was a large model server resident, two render engines up, a desktop session logged in, and the disk at 92% — but a compile is just the CPU chewing on source, so you set MAX_JOBS=8 to get it over with and walked away. Within minutes the box was gone. Not slow: gone, in the exact way a bad model load takes it — ping perfect, sshd dead at the banner, every service port accepting the connection and then answering nothing.

THE LIE / THE TRUTH

THE LIE — what the instrument reports

THE TRUTH — what is physically happening

nvidia-smi --query-compute-apps=pid,used_memory → (build absent)

The compilers never appear on the GPU tool — nvcc, cicc, ptxas hold no CUDA context while they compile. By every GPU instrument the build is invisible. It is "only a build, not a GPU job," so it is safe to run alongside the resident model. The card isn't even involved.

ps --sort=-rss -eo pid,rss,comm → 19 × cicc, ~6 GB each

The compile is a memory load like any other. Each parallel compiler process is several GB of host RAM, and on a unified die host RAM is the pool the model lives in (Plate 05). MAX_JOBS=8 — and the deeper tree it spawns — is a tens-of-GB spike arriving all at once into the same pool. It drove the box into the same swap wedge a too-big model load does.

The GPU tool is telling the truth about its own question and it is the wrong question. "Is this process holding GPU memory?" — no, a compiler holds none. "Is this process about to exhaust the one pool the GPU draws from?" — that is the question, and no GPU counter is watching it. The whole error is the word only: even a discrete-GPU workload needs host memory and CPU resources, so a compile can contend there too. On the GB10 they are the same bytes. A build is not a lighter thing than a model load. It is a model load with a different name.

The OOM kill had culled a couple of victims and relieved the instant, not the source. A box that recovers from a load-wedge and leaves the load running has not recovered; it has rearmed. Failure class: admission without a runtime budget · Escape hatch: release, verify headroom, then load

You compare a 17.4 GB model file with the capacity printed on a 128 GB machine and decide it fits. The arithmetic is tidy because you left out the model already living there. By the time the new load tells you about the omission, the shell you would use to correct it no longer answers. The useful subtraction belonged before the request.

THE LIE / THE TRUTH

THE LIE — capacity mistaken for vacancy

THE TRUTH — the admission question

total: 121 · challenger file: 17.4 GB

The file is much smaller than the machine. Start it.

available: 12

The host is already carrying a large resident. The candidate's weights exceed the reported headroom even before its runtime overhead. Free the conflicting workload and measure again.

A weight file is evidence about one component of the requirement, not a certificate of fit.

The incident, from the log

The failure was not that a reader lacked an obscure command. It was that a known constraint had no force over the next action. The system allowed a model test to begin without confirming that the model could be provisioned alongside the resident. A warning in prose did not reserve any memory.

  1. Load under a measured budget. Allow for the candidate's peak requirement and the services that must remain. Observe startup and readiness. An open TCP port while weights are loading does not prove that the model can answer.

THE CHECK HAS TO OWN THE DECISION

A dashboard can display twelve available gigabytes and still let the next caller spend twenty. Put the admission check in the path that starts the work. If multiple callers can submit, the decision also needs ownership: one caller cannot reserve the same headroom another has just committed.   1. Keep a workload ledger. Record warm and cold peak memory for the configurations you actually use. Include context length, batch size, image resolution and relevant runtime versions. A different configuration is a new budget.
  2. Make release observable. Check the intended service's residency and host headroom after unloading. If the numbers disagree with the expected change, resolve that disagreement before admitting another large job.
  3. Use limits as tested controls. A missing Docker memory limit does not force a process to fill the machine; the application determines its demand. Conversely, adding a limit does not prove safe GPU co-residency. Verify what is charged, what fails at the limit, and whether the OS retains room to recover.
  4. Define the failure path. If the candidate cannot become ready in its expected window, retain the loader logs and use the agreed stop/recovery route. Do not send a second request just because the first caller timed out.
  5. Recalibrate after material changes. A new model, context setting, allocator or driver can change the peak. Keep the last known good budget attached to its configuration, not as a folklore number for the entire machine.

The number on the box is not permission to load. Release the room, measure the room, then spend it.

PLATE 10 · PART III

THE WATCHER GOES AWAY

Failure class: false failure (the poller dies while the work succeeds) · Escape hatch: read the engine's own record — its job history, its output directory — never the poller

This is a standing order, not a war story. A long job on this box runs somewhere you are not watching from: another process, a container, another machine. You submit it and you poll — a spinner in a browser tab, a request handler holding a socket open, a daemon thread ticking a status. The engine can outlive the watcher. When the watcher dies, times out, or navigates away before the job finishes, a real, completed, on-disk result reports to you as it didn't work — and you go hunting a failure that never happened.

THE LIE / THE TRUTH

THE LIE — what the poller reports

THE TRUTH — what is physically on disk

The gallery is empty. The reply finished with no artifact attached. The poll returned an error, or a timeout, or simply nothing — and the log the service writes shows no trace of the request at all.

The render failed. It produced nothing. Submit it again.

The job completed. The engine's own job history has it marked done, and the output file is sitting in the engine's output directory with a real byte count and a real mtime. Nothing failed. The only thing that broke was the thread, tab, or timer that was supposed to carry the result back — and it broke after the work was already safe.

The asymmetry is the whole lesson: the poller and the work have separate lifetimes. The work runs in a process built to run for forty minutes; the poller lives in a browser tab you might close, a request handler with a timeout, or a thread that dies the instant its parent process restarts. Either layer can fail. Establish which one failed before submitting the work again. Treat a missing result as a reporting failure first and a work failure only after the engine's own record has told you the job is genuinely gone.

The incident, from the log

The archetype: a long render — a job whose engine reports a warm baseline near 28 minutes — was submitted, and the process holding the filing thread was restarted about three minutes in. The thread died with its process. The engine kept running on the other machine, finished the clip, and wrote it to its output directory exactly as instructed.   • A poll timeout was read as failure. A watcher gave up after its 40-minute limit and reported error. The render had not stopped — it was still going, and finished later. Without that confirmation, report an unknown outcome rather than promising success or failure.

The page did a real GET navigation that killed its own in-flight fetch POST mid-request. Racy, so it looked intermittent. SILENT LOGS ARE NOT EVIDENCE

The trap that turns a five-minute lookup into an afternoon: you check the service log, see no line for your request, and conclude the request never arrived. It proves nothing. A service started at uvicorn.run(..., log_level="warning") writes no access log at all — its console holds the startup banner and tracebacks and nothing else, so "no POST in the log" is the expected state whether the request succeeded, failed, or was never sent. Worse, buffering and carriage-return progress output can make a short docker logs tail misleading, so a live job's log tail sits frozen on an old line and reads exactly like a hang. Before you reason from a log's silence, know what that service actually logs. The authoritative record is the engine's structured job state — its /history, its in-memory jobs map, its output directory — not the absence of a line in a stream that was never going to print one. And note the second-order trap: an in-memory jobs map is itself a fragile watcher — a restart wipes it, so a genuinely-finished job can vanish from it while the file on disk is untouched. A valid file matched to the job is stronger evidence than a missing log line. Check the actual content.

The order of investigation — when something "produced nothing"

Do these in order. The artifact may exist even when the UI says otherwise.

  1. Did it actually run? Ask the engine, not yourself. Query the render engine's own job history (a ComfyUI-class backend exposes this at /history/<id>; your engine has an equivalent) and list its output directory. Match the job ID to its recorded output, then open or decode the file. A plausible mtime or a nonzero size alone does not prove the requested artifact completed.
  2. Was anything still watching when it finished? Compare the job's end time against your service restarts — timestamped console logs (ls .../logs/*_console_*.log) make this fast. If the process that submitted the job restarted between submit and completion, the filing thread died with it and the result is orphaned, not lost.
  3. Only now suspect the job. An explicit engine error is evidence of failure. An absent record may instead mean history was lost; check the queue and durable submission record before deciding whether to retry. That is the last hypothesis, not the first.

Recovery & prevention

  1. Recover an orphan by re-filing it, not re-rendering it. When the engine's record shows a completed job whose output never got carried back, pull the file from the engine's output directory and file it. Build this as a reconciler that runs at process startup and on demand: sweep every render host for completed jobs whose outputs aren't yet indexed, and adopt them. Re-rendering a clip that already exists wastes a full render slot to reproduce a file you already own. Verify the reconciler on a disposable copied output with its index entry omitted — a sweep that never rescues anything is a sweep you cannot trust.
  2. Make the watcher outlive the work, or make the work self-report. A poller in a tab or a thread is doomed by design. Either move the carry into something as durable as the job (the engine writes the result to its final home itself; the watcher only notices), or accept that the watcher will sometimes die and lean on the startup reconciler to catch what it drops. Do not build the only record of a forty-minute job into a thing that lives thirty seconds.
  3. A timeout reports an unknown outcome until checked. Say "still running" only when the engine confirms it. Otherwise preserve the job ID, report the lost observation, and check before retrying. Reporting error on a timeout is the poller confessing its own impatience as the job's death, and it sends the next operator to re-run a render that was about to finish.
  4. Health-check the record, not the reporter. Before you believe a job failed, hit the layer that holds the truth — the engine's history and its output directory — the same discipline as every plate in this book: read the fact from the layer that actually knows it, not the shallow surface that answers first.

The honest one-liner: a finished job and a living watcher are two different facts, and only one of them is on disk. When they disagree, believe the disk.

What a format name leaves out

GGUF is a container format that can hold several quantisation types. Saying “GGUF versus fp8” does not specify two comparable bit widths. Nor does similar measured speed prove that two implementations move the same number of bytes. One may spend more time in dequantisation, different kernels or cache management. Our deployment change was useful, but it was not a controlled quantisation study.

Lowering weight precision can improve decode throughput when bandwidth is the bottleneck. It can also change kernel support, quality and memory overhead. A four-bit model is not automatically twice as fast as an eight-bit model, and fp16 to fp8 is not automatically irrelevant to speed. Both claims would outrun this incident.

KEEP THE SCORECARD IN SEPARATE COLUMNS

First-token latency, sustained tokens per second, aggregate throughput, tool-call validity and model quality are different outcomes. A runtime may improve one while leaving another unchanged. Prefix reuse can make a familiar prompt cheap without improving long-form generation. A batching benchmark may serve many users efficiently while telling you little about one person's waiting time. Keep the prompt, context, concurrency and cache state beside the number.

The parser improvement belongs to the serving path, not to fp8 as a property. The retained voice is an assessment of this model in use, not a guarantee that a precision will preserve every finetune. The prefill improvement was reported with a runtime and caching change; attributing all of it to quantisation would conceal the part that actually did the work.

Recovery & prevention

  1. Name the baseline exactly. Model revision, quant type, runtime, kernel configuration and hardware. A format family is not a baseline.
  2. Measure the wait and the stream. Record time to first token and sustained decode separately. Use the same prompt, context and output length; report cold and warm conditions.
  3. Use the roofline as a plausibility check. Bandwidth divided by estimated bytes per token helps set expectations. Do not invert the ratio and call seconds per token “tokens per second,” or mix GB and GiB silently.
  4. Change one major factor when making a causal claim. If you replace the runtime and the quant together, report a deployment comparison. It may be exactly the practical comparison you need, but it cannot identify every mechanism.
  5. Keep the benefits that arrived. A stable parser can justify a migration even without faster prose. Report that benefit directly, alongside the unchanged decode rate.

The quant label describes a representation. The stopwatch describes your workload. Keep both.

The link looks redundant. The process name looks specific. The container is running, so surely it will run after the next reboot. None of these impressions tells you what depends on the thing you are about to change. The last plate is a list of dependencies to establish before ordinary housekeeping becomes an outage.

The orders

1. Do not improvise firmware maintenance. Our internal operating notes prohibit mst and mstflint on our GX10s. They do not contain a reproduced failure or a vendor bulletin establishing that merely running either utility bricks every GX10. The book cannot turn that local prohibition into a hardware fact. Our machines retain their local rule. For your machine, use the exact vendor-supported update procedure, matching hardware identity and firmware, with a recovery plan. An inspection command and a firmware-write command are different operations. We have not tested the alleged bricking mechanism.

2. Protect the path you are using to recover. Before changing a NIC, address, route or firewall, establish a second path that actually works. An independent console can be more valuable than three services that all depend on one SSH connection. On our pair, the private ConnectX link was load-bearing. That is our topology, not a property that makes every private cluster cable untouchable. NVIDIA's networking guide describes supported Spark networking; partner hardware still needs its own applicable guidance.

3. Use one owner for model switching. A switch should stop the old resident, verify headroom, start the new workload and wait for readiness. Our lab has a tool for that sequence. There is no universal GB10 “brain-switch” command. Preserve the sequence and its checks, whether your owner is a service manager, script or human runbook. Ask the server's model registry what loaded; a model's prose about its identity is not evidence.

4. Choose restart policy deliberately. Our source notes found a serving container configured with restart=no. That would not return automatically solely through Docker's restart policy. For a mutually exclusive model that must remain stopped after an intentional switch, unless-stopped is often appropriate:

# Configuration example, not a command run for this book.
$ docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' <container>
no

$ docker update --restart unless-stopped <container>
# Verify policy and the deployment's ownership convention.

Both always and unless-stopped respect a manual stop while the current daemon keeps running. The important difference is across daemon restart: always can bring a manually stopped container back; unless-stopped preserves that stopped state. See Docker's restart-policy documentation. Do not configure every mutually exclusive large model to return together after a reboot.

5. Prove boot behaviour. Being a systemd unit does not by itself establish automatic startup or restart-on-failure. Enablement, dependencies, conditions and restart settings matter. A user unit may need a persistent user manager for startup without login. In our incident a render service launched as a detached process did not return as the supervised services did. Inventory the service owner and verify a controlled restart window. See systemd's login manager documentation for user lingering.

6. Stop the exact workload you own. A broad match for server.py once killed our supervisor while targeting a render service. A full-command match can also catch a remote shell containing the pattern. Exact process names reduce one kind of over-match, but pkill -x cicc still targets every matching compiler, including another build. Prefer the owning service, container or cgroup. Otherwise inspect executable, owner and ancestry before acting on verified PIDs.

The incident, from the record

These orders join separate observations: the two-day Wi-Fi loss, the unconfigured container restart policy, the detached render service, the overbroad process kill and the shell-matching trap. They are not one escalating disaster. Keeping them separate matters. The firmware prohibition is an untested local policy; the access loss and mistaken process termination were observed. A book about evidence should not make the former sound more certain than the latter.

THE RECOVERY PATH IS ALSO A DEPENDENCY

A repair dashboard that calls SSH cannot repair a host whose only SSH route you just removed. A supervisor you killed cannot restart the service you meant to target. Before a change, draw the path from your hand to the action and back to its confirmation. If both directions depend on the component being changed, prepare another way in first.

Recovery & prevention

  1. Record actual topology. Interface names, addresses, routes and a tested independent console. Several boxes on a diagram do not prove several paths.
  2. Keep ownership explicit. One authoritative switch path, an intentional boot policy, and identified service boundaries make cleanup predictable.
  3. Separate inspection from mutation. Read-only identification precedes a process stop or network change. Firmware writes require the applicable hardware procedure.
  4. Verify the effect. Confirm the intended workload stopped, unrelated services survived, and the promised access path still works. The command exiting successfully is only the beginning of that check.

Maintenance is work on the dependencies you usually take for granted. Name them before touching them.
